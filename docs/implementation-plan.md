# Milestone-controlled commerce implementation plan

Only milestone 0 is authorized now. M1–M10 and optional M11 are unstarted and require approval. Teach problem→show pinned source/tests→discuss alternatives→obtain milestone approval→generate owner/Codex code within scope→validate/debug→explain paths→ask understanding questions→record evidence. Code generation alone is not completion.

## M0 — Research and planning

**Objective:** original commerce/authority/agent design backed by Medusa/AP2/LangGraph and selective secondary source research. **Concepts:** user authority versus processor authorization, seven distinct states, replay and compensation. **Architecture/interfaces/tasks:** requirements/domain/policy/tools/payment contracts, all ten AC scenarios, evaluation/security design, README/ADRs/roadmaps. **Tests/review:** source/license/citation checks, diagram/link/consistency/secret/docs-only validation and GitHub verification. **Failures:** unsupported protocol claims, copying old PayOps scope, deleting unconfirmed repository. **Done:** meaningful reviewed documentation; no application code. **Interview:** why not just an agent with a payment tool? **Dependencies:** master plan; old repository deletion has separate final confirmation.

## M1 — FastAPI, PostgreSQL and durable session foundations

**Objective:** smallest persisted purchase-session/status boundary with no payments. **Learn:** Python typing/errors/async, Pydantic DTOs, FastAPI, SQLAlchemy transaction scope, Alembic, pytest/Testcontainers. **Architecture/interfaces:** session resource, trusted synthetic user/agent context, error envelope, session revision and durable job-intent concept. **Tasks:** create minimal build/API/schema during approved work; validate request and persist/query safe state. **Tests:** actual DB commit/rollback/restart, invalid input, actor mismatch and duplicate request identity. **Failures:** disconnect DB, lose response after commit. **Done:** stable sessions survive restart; no in-memory false durability, no purchase capability yet. **Tradeoff:** async request handling versus background work. **Interview:** what commits before returning 202? **Dependencies:** M0 review and M1 approval.

## M2 — Virtual kiosk catalog, inventory and order model

**Objective:** deterministic small catalog/price/stock/order domain before LLM tools. **Learn:** money minor units, quote/version, stock versus reservation, SQL constraints and row locks. **Architecture/interfaces:** kiosk/product/price/inventory/quote/order records; exact filters and immutable quote resource; no execution before permission. **Tasks:** implement data model/query/quote and pure invariant logic; define reservation port and staged order behavior, delaying financial dispatch to M6. **Tests:** price/currency/overflow, unavailable SKU, scope, quote expiry and available=stocked−reserved. **Failures:** stale catalog/changed quote, wrong merchant/product. **Done:** repeatable synthetic catalog and authoritative quote; no claim stock display reserves inventory. **Tradeoff:** one product/currency versus full commerce engine. **Interview:** quote versus order versus reservation? **Dependencies:** M1; Medusa/Saleor references.

## M3 — Initial single LangGraph purchasing workflow

**Objective:** bounded interpret→select→clarify/status graph without consequential execute authority. **Learn:** state/reducers/nodes, structured outputs, tokens/context budgets, fake provider, graph termination. **Architecture/interfaces:** typed intent, session/run identity, allowed kiosk context, bounded errors and tentative candidates. **Tasks:** implement graph/fake model, safe output parsing/refusal and basic trace metadata; real model only after usage approval/current limit/price check. **Tests:** invalid schema/refusal/loop/ambiguous request, reducer replay and no unauthorized tools. **Failures:** LLM timeout, truncated response, invented product. **Done:** graph terminates/clarifies and cannot buy or approve. **Tradeoff:** rule workflow versus adaptive choice; baseline preserved. **Interview:** what does LangGraph own versus commerce? **Dependencies:** M2.

## M4 — Product discovery and structured tools

**Objective:** exact catalog/quote/status tools bound to trusted user/agent/source. **Learn:** tool proposals versus authorized dispatch, schema/semantic validation, safe descriptions and context bounds. **Architecture/interfaces:** fixed registry, typed error/provenance envelope, candidate comparison and quote refs; no raw URL/SQL/payment. **Tasks:** implement product search/get_quote/get_status and logical call identity, permission guards and structured constraint validators. **Tests:** cross-user/kiosk refs, oversize/malformed/injected descriptions, invalid product/price and unsupported tool. **Failures:** source unavailable versus no eligible products, fake model “success.” **Done:** agent selects valid candidates or asks clarification; cannot execute. **Tradeoff:** structured filters before optional RAG. **Interview:** can schema-valid arguments still violate permission? **Dependencies:** M3; AC-09/10 negatives begin here.

## M5 — Human approval and deterministic policy

**Objective:** trusted exact purchase approval and backend enforcement before any execution tool. **Learn:** authN/authZ, quote/hash/version binding, one-use nonce, expiry, actor scope and trusted UI. **Architecture/interfaces:** approval request/decision/receipt, policy evaluator, minimally safe React approval view or equivalent trusted frontend; immutable authoritative fields. **Tasks:** implement approval display/decision, owner identity, exact term checks, replay/denial audit; keep raw signer/payment credentials outside graph. **Tests:** AC-01/03/06/09/10 approval omissions, tamper, wrong actor, stale/expired quote, forged grant and duplicate decision. **Failures:** price changes while approval page open, malicious product HTML, UI reload. **Done:** backend rejects absent/altered approval regardless of model behavior. **Tradeoff:** exact approval versus maximum-only consent. **Interview:** hash versus signature versus consent? **Dependencies:** M4; no autonomous delegation yet.

## M6 — Complete human-approved checkout slice

**Objective:** AC-01/03/04/05 through standalone payment/dispense simulators. **Learn:** transactional stock/budget/order acceptance, idempotency, provider uncertainty, saga and immutable execution identity. **Architecture/interfaces:** checkout execution endpoint, reservation/order/job records, thin payment port and stable dispenser command; authorize→dispense→capture. **Tasks:** implement deterministic acceptance transaction and bounded coordinator, actual-state monitoring and core cancel/failure branches; enable only approved-business-action tool. **Tests:** last-item and duplicate execution races, response loss, no dispense before known authorization, no false success, price revalidation. **Failures:** commit-before-reply, payment/dispense effect-then-drop, failed dispense and unknown compensation. **Done:** human-approved independent demo works, stock/usage/effects correct; no delegated autonomy until this gate passes. **Tradeoff:** capture-after-dispense recovery exposure versus captured-before-dispense refund exposure. **Interview:** why no global rollback? **Dependencies:** M5; full recovery corpus M8/M9.

## M7 — Delegated authority, revocation and replay

**Objective:** AC-02/06/10 with enforceable scoped grants after human path completion. **Learn:** user versus agent identity, per-purchase/total/count limits, atomic usage reservation, revocation linearization, signing trust and replay. **Architecture/interfaces:** versioned grant/revoke/status APIs and exact per-execution binding; immutable nonce/usage identities. **Tasks:** implement policy constraint registry, trusted grant UI, usage ledger, current-state checks, explicit refund-budget restoration policy and in-flight revocation semantics. **Tests:** concurrent cap race, wrong merchant/SKU/currency/actor, expired/revoked version, signature/nonce tamper, replay and revoke-during-dispatch. **Failures:** clock boundary, stale permission cache, accepted operation completes after revoke. **Done:** no backend out-of-scope effect; honest in-flight limitations and audit. **Tradeoff:** exact allowlists versus semantic categories; project contract before AP2 wire implementation. **Interview:** why a signed token cannot enforce concurrent budget alone? **Dependencies:** M6 verified complete.

## M8 — Durable agent/business execution and concurrent recovery

**Objective:** AC-04/05/08 under crashes, pauses, redelivery and human/source waits. **Learn:** Postgres checkpointing, interrupt replay, application effect identity, jobs/outbox, leases/fences and saver write ownership. **Architecture/interfaces:** durable scheduler, per-run checkpoint thread, logical tool-result store, current-owner guarded business finalization; serialized graph runner initially. **Tasks:** implement checkpoints/resume, DB job sweeper and safe reservation expiration; Celery/Redis only if it adds demonstrated value, carrying IDs not truth. **Tests:** every DB/checkpoint/remote effect/ack gap, paused old owner and lost lock connection, duplicate resume, missing checkpoint with extant execution, optional Redis loss. **Failures:** reclaim job while old worker resumes; unknown dispense TTL. **Done:** no repeated purchase/dispense; stale saver writes prevented before parallel takeover, otherwise documented serialized limitation. **Tradeoff:** DB runner versus Celery/Temporal. **Interview:** checkpoint versus idempotency? **Dependencies:** M7; includes AC-08 plus source grounds.

## M9 — Java integration and fulfillment compensation

**Objective:** contract-tested integrated purchase and AC-07/08 recovery while independent modes remain usable. **Learn:** versioned HTTP/events, source observations, auth scopes, outbox/inbox and deterministic compensation. **Architecture/interfaces:** Java payment adapter, optional Kafka observations with inquiry fallback, service-scoped compensator, shared synthetic fixture version. **Tasks:** implement command mappings and canonical source reads, no shared DB; complete authorized-failed-dispense cancel branch, captured-failed-dispense refund branch and unknown holds. **Tests:** PS/AC matrix, denied amount/scope/hash, duplicate/reordered events, refund/capture races, late dispense/capture and compensation unknown. **Failures:** stop Java/broker, crash compensator, replay old event. **Done:** Java and commerce demos work independently and integrated, with one intended effect and factual final report. **Tradeoff:** manual capture default versus early-capture fixture. **Interview:** why not let the agent choose refund? **Dependencies:** commerce M8 and Java financial/recovery APIs; not entire Java deployment/recon completion.

## M10 — Evaluation, security, observability and approved deployment

**Objective:** full AC corpus and measured quality/reliability/cost plus reproducible demonstration UI. **Learn:** oracle leakage, multi-valid selection labels, policy versus probabilistic metrics, injection threats, tail latency/cost denominators and operational tracing. **Architecture/interfaces:** versioned eval artifacts, Langfuse/OTel metadata, rule/fixed/agent baselines, local dashboards and k6 fake-provider load. **Tasks:** implement harness/security/failure tests and UI/audit views; publish only real results. Docker/CI/ECS configuration and billable calls/deployment require explicit scope/cost approval. **Tests:** all ten ACs, source unknown, ambiguity, wrong actor, leakage canary, overload and counter reconciliation. **Failures:** quota/time budget exhaustion, malicious receipt, fake model versus real-provider comparison. **Done:** hard gates pass, failures/limits reported, independent/integrated setup documented; cloud can remain explicitly deferred. **Tradeoff:** usefulness versus cost/latency, trace detail versus privacy. **Interview:** demonstrate agent value over baseline with evidence. **Dependencies:** M9 for integrated results; evaluation/policy tests accompany earlier milestones rather than waiting here.

## Optional M11 — Interoperability, external identity and isolation

**Objective:** adopt one protocol/identity/isolation extension only if a concrete interoperability/security requirement exists. **Learn:** pinned AP2/UCP/ACP/TAP requirements, trust enrollment/credentials, conformance versus demo, relationship authorization or sandbox lifecycle. **Architecture/interfaces:** version adapter around stable core; no replacement of financial/stock invariants. **Tasks:** select actual target and applicable tests; implement one scoped adapter/identity integration after approval. OpenFGA/MCP/Temporal/Kubernetes require separate justification and ADR. **Tests:** protocol positive/negative conformance, wrong key/audience/replay, discovery/version mismatch, permission isolation and unchanged AC regression. **Failures:** external registry unavailable, expired credential and compromised untrusted tool output. **Done:** specific demonstrated compatibility statement with version/test evidence; no blanket badge. **Tradeoff:** interoperability value versus maintenance and new trust surface. **Interview:** what does authenticated agent identity not authorize? **Dependencies:** M10 correctness/evaluation and explicit optional scope approval.
