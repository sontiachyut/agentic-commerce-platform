# Source-based reference analysis

**Baseline:** 2026-10-21. Public repository heads were resolved to the exact SHAs below; complete tree manifests and selected source/test files were inspected. Tests were **read, not executed**; no reference applications, model calls, containers or payment APIs were run. Static evidence is distinguished from documentation and our proposed design. No reference implementation is copied into this repository.

Medusa is the primary reference for commerce domain/workflow boundaries, AP2 for verifiable purchase authority, and LangGraph for agent orchestration/recovery. None alone solves the combined inventory/payment/authorization problem. A protocol sample is not a mature deployed payment processor.

**Use cases/scenarios:** AC-03 quote refresh, AC-04 stock race, AC-05 order replay, AC-07 compensation, AC-08 recovery. **Adopt:** explicit reservation records, separate payment/fulfillment, immutable order snapshot, repeat-completion guard, compensating work. **Reject/simplify:** Medusa's full module graph, shipping/promotions/tax engine, plugin ecosystem, TypeScript translation, and assuming workflows form one distributed SQL transaction.

**Proposed equivalent:** small Python commerce modules, PostgreSQL row locks/conditional updates and unique checkout/order identities, durable saga jobs and narrow payment/dispenser ports. Reserve before external authorization in our default flow; this is our deliberate ordering, not a claim to reproduce Medusa. Tradeoff: stronger local reasoning and less functionality versus full commerce extensibility. Authorization-before-dispense-before-capture avoids charging known failed dispensing but requires recovery if capture fails after dispensing.

**Limits:** selected workflow/service/test inspection does not establish every deployment's locking provider, timeout behavior or compensation success. Medusa can represent pending authorization; our kiosk must still block dispensing until its required payment evidence is confirmed.

**License:** pinned [LICENSE](https://github.com/medusajs/medusa/blob/f7add009dd2f142d98090a5194750e71b2147ddf/LICENSE) states MIT except identified enterprise materials; [ENTERPRISE-LICENSE](https://github.com/medusajs/medusa/blob/f7add009dd2f142d98090a5194750e71b2147ddf/ENTERPRISE-LICENSE.md) enumerates exclusions including RBAC/SSO paths. Do not label the whole current repository unconditionally MIT or reuse enterprise code based only on public availability. Our policy design is original; no Medusa source is embedded.

## UCP versus ACP decision

UCP emphasizes negotiated capabilities/discovery and extensible commerce/payment handlers; the inspected checkout page discovers handlers through a UCP profile and checkout metadata, with a separate AP2 extension. ACP's inspected version supplies concrete checkout/delegated-payment API/schema contracts and explicit idempotency responses. Neither replaces backend stock, grant budgets, effect identity or compensation. Their versions and evolution differ; do not claim they are interchangeable or one universally superior.

MVP uses a small project-specific typed REST contract and simulated payment port. Optional adapters can map a deliberately selected protocol version without changing core policy/state. Evaluate actual merchant/client interoperability demand, available conformance suite, identity/credential handling, schema surface and maintenance cost before choosing UCP or ACP. No broad protocol implementation or compatibility badge is justified now.

## Research gaps and application consequences

No vendor test suite, model evaluation or protocol conformance suite was executed; no production guarantees are inherited. Our novel acceptance work includes grant revocation versus dispatch, atomic budget+last-stock reservation, uncertain dispensing, cross-system compensation and stale checkpoint ownership. These gaps become explicit AC tests, not handwaved by framework adoption.

Hyperswitch and Java payment research are in the [payment repository's analysis](https://github.com/sontiachyut/payment-processing-cleanroom-implementation/blob/main/docs/reference-analysis.md). The two projects share contracts, not vendor internals. All future reuse requires actual file-level license/notice review; public visibility or a GitHub license summary alone is insufficient.
